# 영속성

같은 데이터 + 같은 시드 + 같은 명령 = 같은 상태다. 그래서 **명령 로그가 원본**이고, 스냅샷은 복구를 빠르게 하는 캐시이며, 해시는 둘이 어긋났는지 검증하는 수단이다.

## 1. 파일

```
<state-dir>/<match-id>/
├── commands.log            # 명령 + 해시. append-only
└── snapshots/
    └── 000000000720.snap   # 파일 이름 = 틱
```

## 2. 인코딩

로그 레코드와 스냅샷은 코어의 정규 바이너리 인코딩([state.md §5](state.md))을 쓴다. Protobuf는 와이어 전용이다.
Protobuf 직렬화는 같은 메시지라도 구현과 버전에 따라 바이트가 달라질 수 있어서(정규형을 보장하지 않는다) 해시 입력으로 쓸 수 없고, 와이어 스키마가 바뀔 때마다 저장 형식이 흔들리는 것도 피하고 싶기 때문이다.

## 3. 명령 로그

- **헤더**: 매직, 형식 버전, `sim_version`, match ID, 시나리오 키, 시드, 데이터 해시.
- **레코드**: `[길이 u32][종류 u8][본문][CRC32C u32]`

  | 종류 | 본문 | 언제 |
  |---|---|---|
  | `COMMANDS` | 틱, 명령 목록 (진영 + 명령 본문, 접수 순서 그대로) | 명령이 있는 틱만. **그 틱의 `Step` 전에** 기록 |
  | `HASH` | 틱, 상태 해시 (SHA-256) | `hash_interval`(기본 24)틱마다 |

- 명령이 없는 틱은 레코드가 없다. 입력이 없으면 결과가 이미 정해져 있다.
- 배속과 일시정지는 기록하지 않는다. 결과에 영향이 없다.
- `sim_version`은 규칙 코드가 결과를 바꾸는 방식으로 변할 때 올리는 상수다.
- **내구성**: 레코드는 쓸 때마다 OS에 넘긴다 (프로세스가 죽어도 유실 없음). `fsync`는 `HASH` 레코드, 스냅샷, 정상 종료 때 한다. 따라서 OS나 전원 장애에서는 최대 `hash_interval`틱이 유실될 수 있다.

## 4. 스냅샷

- `snapshot_interval`(기본 720, `hash_interval`의 배수)틱마다, 그리고 정상 종료할 때. 정상 종료 때는 그 틱의 `HASH` 레코드도 함께 남긴다.
- 내용: 헤더(매직, 형식 버전, `sim_version`, match ID, 데이터 해시, 틱, 상태 해시) + `State`의 정규 인코딩 + CRC32C.
- 방 고루틴은 메모리에 인코딩하는 데까지만 하고, 디스크 쓰기는 별도 고루틴이 한다. 임시 파일에 쓰고 `fsync`한 뒤 rename으로 교체한다 (쓰다 만 스냅샷이 남지 않는다).
- 최근 3개만 보관한다.
- 순서 불변식: 스냅샷을 쓰기 전에 로그를 그 틱까지 `fsync`한다. 스냅샷이 로그보다 앞서는 일이 없다.

## 5. 복구

서버를 시작할 때 match 디렉토리가 있으면:

1. 로그 헤더의 데이터 해시와 `sim_version`을 현재 값과 비교한다. 다르면 복구를 거부한다 (결과가 달라지므로). 시드는 서버 옵션이 아니라 로그 헤더의 값을 쓴다.
2. 가장 최신의 유효한 스냅샷을 읽는다 (CRC와 상태 해시 검사. 손상됐거나 로그의 마지막 틱보다 앞서 있으면 그 이전 것). 없으면 시나리오 초기 상태에서 시작한다.
3. 로그에서 스냅샷 틱 이후의 레코드를 재생한다. `HASH` 레코드를 만날 때마다 대조하고, 다르면 중단하고 오류를 낸다.
4. 끝이 잘린 레코드(크래시 흔적)는 버리고 그 지점부터 이어 쓴다.
5. 로그에 남은 마지막 틱에서 일시정지 상태로 시작한다. 클라이언트는 재접속해 풀 스냅샷을 받는다.

복구 지점은 "로그에 남은 마지막 틱"이다. 그 뒤에 명령 없이 진행됐던 틱은 되감기지만, 입력은 하나도 잃지 않는다.

## 6. 리플레이 검증

`sandtable-replay`는 스냅샷을 무시하고 로그를 틱 0부터 재생해 모든 `HASH` 레코드와 대조한다. 옵션으로 각 스냅샷도 같은 틱의 재생 상태와 비교한다. 다르면 첫 불일치 틱을 출력하고 0이 아닌 코드로 종료한다.

## 7. 1단계의 한계

- 로그는 파일 하나로 계속 커진다 (분할·압축 없음).
- 규칙 코드나 데이터를 바꾸면 기존 로그는 재생할 수 없다. `sim_version`과 데이터 해시로 감지만 한다.
- 세션(누가 어느 진영인지)은 저장하지 않는다.
