# 2단계 계획: 웹 뷰어 클라이언트

> **상태: 구현 완료.** 이 문서는 구현을 맡을 세션에게 준 작업 지시서였다. 계획과 달라진 점은 맨 아래 [§10](#10-계획과-달라진-점)에 적었다.

1. [README.md](README.md) : 원칙과 레포 구조. **특정 게임명(상표)을 코드·문서·UI 문자열 어디에도 넣지 않는다.**
2. [protocol.md](protocol.md) : 클라이언트가 말해야 하는 프로토콜 전부.
3. [state.md](state.md) §6, [rules.md](rules.md) §1·§7 : 뷰에 무엇이 들어오는지, 이동 진행도를 어떻게 해석하는지.
4. `proto/sandtable/v1/sandtable.proto` : 와이어 형식의 기준.
5. `server/cmd/sandtable-cli/main.go` : 동작하는 참조 클라이언트 (약 200줄). 스냅샷과 델타를 다루는 순서가 그대로 들어 있다.

시작 전에 `make test`가 통과하는지 확인하고, 끝날 때도 통과해야 한다.

## 1. 목표

브라우저에서 지도를 보면서 마우스로 플레이할 수 있게 한다. 터미널 CLI를 대체한다.

**완료 기준**: 브라우저 탭 두 개로 각각 다른 진영에 접속해서, 로비에서 시작하고, 사단을 클릭해 인접 프로빈스를 공격하고, 전투·후퇴·점령·안개가 지도에서 눈으로 구분되며, 탭을 새로고침해도 같은 진영으로 다시 들어온다.

## 2. 정해진 것

| 항목 | 결정 |
|---|---|
| 플랫폼 | 웹 브라우저 |
| 지도 | 영역으로 채운 지도. 프로빈스 좌표에서 경계를 자동 계산 (Voronoi) |
| 위치 | `client/` (지금은 `.gitkeep`만 있다) |
| 언어·도구 | TypeScript + Vite, 패키지 관리는 npm (이 머신에 Node 24가 있다) |
| 프레임워크 | 없음. 지도는 Canvas 2D, 패널과 버튼은 일반 DOM |
| Protobuf | `@bufbuild/protobuf` + `protoc-gen-es`. 생성 코드는 `client/src/gen/`에 두고 커밋 |
| Voronoi | `d3-delaunay` |
| 테스트 | Vitest (상태 저장소, 좌표 계산). 화면은 Playwright로 스크린샷을 찍어 직접 확인 |
| UI 언어 | 한국어. 문자열은 `client/src/strings.ts` 한 파일에 모은다. 코드·주석·식별자는 영어 |

런타임 의존성은 위 두 개(`@bufbuild/protobuf`, `d3-delaunay`)로 끝낸다. 더 필요하면 이유를 적고 추가한다.

Canvas를 고른 이유: 샘플 맵은 16칸이지만 실제 맵은 수천 칸이 된다. SVG는 그 규모에서 느려진다.

## 3. 원칙

- **클라이언트는 시뮬레이션하지 않는다.** 서버가 준 상태를 그리고 명령(의도)을 보낼 뿐이다. 이동 결과 예측, 전투 계산, 경로 탐색을 클라이언트에 구현하지 않는다. 경로는 서버가 `DivisionView.path`로 준다.
- **`server/internal/sim`은 건드리지 않는다.** 규칙을 바꾸면 골든 해시가 깨지고 기존 로그를 재생할 수 없다. 서버 변경은 §4에 적힌 것만 한다.
- 스냅샷과 델타의 의미는 `server/internal/view/view.go`의 `Apply`와 정확히 같아야 한다.
- 클라이언트가 알 수 없는 정보(안개 뒤의 사단 등)를 추측해서 그리지 않는다.

## 4. 서버 쪽 변경 (작게)

1. **정적 파일 제공.** `sandtable-server`에 `-web` 플래그(기본 `../client/dist`)를 추가하고, 그 디렉토리가 있으면 `/`에서 제공한다. `/ws`는 그대로다. 위치: `server/internal/transport/server.go`의 `Handler`.
2. **접속 전 방 정보.** 지금은 `Hello`에 진영 키를 넣어야 하는데, 진영 목록은 `Welcome`에 들어 있어서 접속 전에는 알 수 없다. `GET /api/match?id=<match>`를 추가해 JSON으로 돌려준다:
   ```json
   {"id":"default","phase":"LOBBY","tick":0,
    "factions":[{"key":"azure","name":"Azure League","taken":true,"player":"alice"},
                {"key":"crimson","name":"Crimson Pact","taken":false}]}
   ```
   `match.Match`에 상태를 방 고루틴에서 읽어 오는 메서드를 하나 추가한다 (`Snapshot()`과 같은 방식: `inbox`로 함수를 보내고 결과를 기다린다). 방 상태를 다른 고루틴에서 직접 읽으면 안 된다.
3. `buf.gen.yaml`에 `protoc-gen-es` 플러그인을 추가하고 `Makefile`에 `client`(빌드), `client-dev` 타깃을 추가한다. `make build`가 클라이언트도 빌드하게 한다.
4. `transport/e2e_test.go`에 `/api/match` 응답 검사를 추가한다.

개발 중에는 Vite 개발 서버(5173)가 `/ws`와 `/api`를 8080으로 프록시한다 (`vite.config.ts`의 `server.proxy`, `/ws`는 `ws: true`).

## 5. 구조

```
client/
├── index.html
├── package.json, tsconfig.json, vite.config.ts
└── src/
    ├── main.ts          # 화면 전환: 접속 → 게임
    ├── strings.ts       # UI 문자열
    ├── gen/             # protoc-gen-es 생성 코드 (커밋)
    ├── net.ts           # WebSocket, 인코딩/디코딩, 재접속
    ├── store.ts         # 정적 데이터 + 현재 뷰. 스냅샷/델타 적용. DOM을 모른다
    ├── geometry.ts      # Voronoi 셀, 프로빈스 찾기, 진행도 → 좌표
    ├── render.ts        # Canvas 그리기
    ├── input.ts         # 마우스·키보드 → 선택, 명령
    └── ui/              # 상단 바, 접속 화면, 사단 패널, 알림
```

`store.ts`와 `geometry.ts`는 DOM 없이 테스트할 수 있어야 한다.

## 6. 단계

각 단계는 끝에 적힌 확인을 통과한 뒤 다음으로 간다.

### M1. 접속과 상태 동기화 (화면 없이)

- Vite 프로젝트 생성, Protobuf 코드 생성, `net.ts`, `store.ts`.
- `store`: `Welcome`으로 정적 데이터와 내 진영을 저장하고, `Snapshot`으로 뷰를 교체하고, `Delta`를 적용한다 (프로빈스 레코드 교체 → `removed` 삭제 → 사단 추가/교체, ID 순 유지).
- `Delta.tick`이 직전 값 + 1이 아니면 연결을 끊고 재접속한다.
- `session_token`을 `sessionStorage`에 저장하고 재접속할 때 `Hello`에 넣는다. 새로고침해도 같은 진영을 되찾기 위해서다.
- **확인**: Vitest로 스냅샷 + 델타 적용 테스트 (추가, 변경, `DESTROYED`, `OUT_OF_SIGHT`, 틱 건너뜀). 브라우저 콘솔에 틱이 올라가는 것이 찍힌다.

### M2. 지도

- `geometry`: 프로빈스 좌표로 Voronoi를 만들고, 좌표 범위에 여백을 둔 사각형으로 자른다.
- 프로빈스 찾기는 "가장 가까운 좌표"다 (`delaunay.find`). Voronoi 셀의 정의가 그것이므로 다각형 판정이 필요 없다.
- `render`: 통제 진영 색으로 채우기, 통행 불가 지형은 물 색, 통제자가 다른 경계는 굵게, 거점 표시, 프로빈스 이름, 지형은 옅은 무늬나 글자.
- 안개: `visible`이 아닌 프로빈스는 어둡게 덮는다. 통제자 색은 유지한다 (통제자는 공개 정보다).
- 휠로 확대/축소, 드래그로 이동.
- 진영 색은 진영 ID로 고정 팔레트에서 고른다 (최소 8색, 인접한 색이 헷갈리지 않게).
- **확인**: Playwright 스크린샷에서 16개 영역, 두 진영 색, 호수, 안개가 구분된다.

### M3. 사단

- 사단은 프로빈스 중심에 카운터(작은 상자)로 그린다. 유닛 타입 글자, 진영 색 테두리, 병력 막대와 조직력 막대.
- 한 프로빈스에 여러 개면 가로로 늘어놓고, 넘치면 `+N`으로 접는다.
- 이동 중인 자기 사단: 경로를 선으로, 다음 프로빈스 쪽으로 진행도만큼 치우쳐 그린다. 진행도 비율 = `progress / (distance(현재, 다음) × move_cost(다음 지형))`. 값은 모두 `Welcome.static`에 있다.
- 전투 중인 프로빈스(`in_battle`)는 테두리를 깜빡이거나 아이콘을 띄운다. 자기 사단 중 다음 프로빈스가 전투 중이면 공격 화살표를 그린다.
- 후퇴 중인 사단은 반투명하게.
- **확인**: CLI 클라이언트로 반대 진영을 조종하면서 스크린샷으로 이동, 전투, 후퇴, 점령, 시야에 들어오고 나가는 사단을 확인한다.

### M4. 조작

- 왼쪽 클릭: 사단 선택 (Shift로 여러 개, 빈 곳 클릭으로 해제). 자기 사단만 선택된다.
- 오른쪽 클릭: 선택한 사단들을 그 프로빈스로 `MoveDivision`. 사단마다 `client_seq`를 올려 보낸다.
- `CommandResult`가 거부면 사유를 한국어 알림으로 띄운다 (거부 사유 enum → `strings.ts`).
- 프로빈스 클릭: 이름, 지형, 통제자, 거점 여부 패널. 사단 선택: 이름, 타입, 병력, 조직력, 보급, 목적지 패널.
- 단축키: `Space` 일시정지/재개, `1`~`5` 배속, `Esc` 선택 해제.
- 오른쪽 클릭의 브라우저 기본 메뉴는 Canvas 위에서 막는다.
- **확인**: Playwright로 선택 → 오른쪽 클릭 → 서버에서 사단이 움직이는 것까지 자동으로 한 번 돌린다.

### M5. 접속 화면과 상단 바

- 접속 화면: 이름 입력, `/api/match`로 받은 진영 목록에서 선택 (이미 잡힌 진영은 비활성, 누가 잡았는지 표시), 방 단계 표시.
- 로비: 참가자 목록, 호스트에게만 "시작" 버튼.
- 상단 바: 틱을 "N일차 HH시"로 표시 (1틱 = 1시간), 일시정지 버튼, 배속 1~5 (호스트가 아니면 비활성), 참가자 목록, 연결 상태.
- 연결이 끊기면 화면에 표시하고 2초 간격으로 재접속한다. `fatal` 오류(`FACTION_TAKEN` 등)면 접속 화면으로 돌아간다.
- §4의 서버 변경을 여기서 마무리하고 `make build` 후 서버 하나만 띄워 `http://127.0.0.1:8080`에서 전부 되는지 본다.
- **확인**: §1의 완료 기준을 처음부터 끝까지 수행한다.

## 7. 함정

- **`uint64`는 `bigint`로 온다.** `protobuf-es`에서 `tick`, `apply_tick`이 `bigint`다. `number`와 섞어 비교하면 조용히 틀린다. `store`에 넣을 때 `Number()`로 바꾸고 그 뒤로는 `number`만 쓴다 (2^53 틱은 도달할 수 없다). `progress`(`int64`)도 같다.
- **기본값 필드는 와이어에 없다.** proto3는 0, `false`, 빈 문자열을 보내지 않는다. 델타의 사단 레코드는 "바뀐 필드"가 아니라 **레코드 전체**이므로, 받은 레코드로 통째로 교체해야 한다. 기존 값과 병합하면 0이 된 값이 옛 값으로 남는다.
- **타 진영 사단의 `path`, `progress`, `supply`는 항상 비어 있다.** `own`이 `false`면 그 필드를 그리지 않는다.
- **일시정지 중에는 `Delta`가 오지 않는다.** 델타가 안 온다고 연결이 죽었다고 판단하면 안 된다. 연결 상태는 WebSocket 이벤트로만 판단한다.
- **명령은 다음 틱에 적용된다.** 오른쪽 클릭 직후에는 화면이 바뀌지 않는다. 클라이언트가 미리 경로를 그려 넣지 않는다. 일시정지 중에 내린 명령은 재개 후에 반영된다.
- **프로빈스 ID는 배열 인덱스다.** `Welcome.static.provinces[i]`의 ID가 `i`, 진영 ID는 `factions` 인덱스 + 1, `0`은 "없음"이다.
- **WSL 경로.** 레포가 `/mnt/e`(Windows 드라이브)에 있어 `npm install`과 Vite 파일 감시가 느리다. 감시가 안 먹으면 `server.watch.usePolling`을 켠다.
- **브라우저 캐시.** 서버가 `index.html`을 캐시하지 않도록 `Cache-Control: no-cache`를 붙인다. 해시가 붙은 `assets/`는 그대로 둔다.

## 8. 하지 않는 것

실제 지리 맵, 손으로 그린 프로빈스 모양, 애니메이션 보간(틱 사이를 부드럽게 잇기), 소리, 모바일 화면, 관전자 모드, 전투 상세 창(전선/예비대 목록), 여러 방 목록 화면. 전투 상세 창은 서버가 전선/예비대 정보를 뷰에 넣어 줘야 해서 프로토콜 변경이 필요하다. 필요해지면 별도로 계획한다.

## 10. 계획과 달라진 점

구현하면서 정한 것들이다. 번호로 짚어서 바꿔 달라고 하면 된다.

1. **`SERVER_SHUTDOWN`, `SLOW_CONSUMER`는 접속 화면으로 가지 않고 재접속한다.** 둘 다 `fatal`이지만 같은 `Hello`로 다시 들어가는 것이 맞는 경우다 (서버 재시작, 느린 연결). 나머지 `fatal` 오류(`FACTION_TAKEN`, `UNKNOWN_FACTION` 등)는 계획대로 접속 화면으로 돌아가고 저장한 세션을 지운다.
2. **이동 중인 사단은 경계까지만 치우친다.** 진행도 비율이 1이어도 사단은 도착 전까지 출발 프로빈스에 있으므로 ([rules.md §1](rules.md)), 카운터는 두 프로빈스 좌표의 중간(경계)까지만 간다. 공격이 막혀 진행도가 찬 사단은 경계에 붙어 공격 화살표를 낸다.
3. **보낸 명령의 표시.** 오른쪽 클릭 직후 목적지 프로빈스에 점선 원을 그리고, 명령의 `apply_tick`이 지나면 지운다. 경로를 미리 그리지는 않는다 (경로는 다음 델타의 `path`로 그린다). 일시정지 중에 명령을 내리면 아무 반응이 없어 보이는 것을 막기 위해서다.
4. **`+N`과 프로빈스 패널.** 접힌 사단은 `+N`을 클릭하면 열리는 프로빈스 패널의 사단 목록에서 고를 수 있다. 칸에 들어가는 카운터 수는 확대 정도에 따라 바뀌지만, 아무리 축소해도 카운터 1개(자기 사단이 있으면 자기 사단)는 보인다.
5. **상단 바에 "나가기" 버튼.** 저장한 세션을 지우고 접속 화면으로 돌아간다. 이것이 없으면 그 탭에서 다른 진영으로 바꿀 방법이 없다.
6. **배속 단축키는 호스트가 아니면 보내지 않고** 알림만 띄운다 (보내면 서버가 `NOT_HOST`로 답한다).
7. **이름 기억.** 접속 화면의 이름은 `localStorage`에 기억해 다음에 채워 둔다. 세션(진영과 토큰)은 계획대로 탭별 `sessionStorage`다.
8. **지형 표시.** 무늬는 지형 키(`forest`, `hills`, `mountain`, `urban`, `lake`)로 고른다. `plains`는 무늬 없음이고, 목록에 없는 지형 키는 프로빈스 이름 아래에 지형 이름을 글자로 쓴다. 칸이 작아 이름이 넘치면 이름을 생략한다.
9. **진영 색** 10색 팔레트. 지도 채우기는 이름이 읽히도록 진영 색을 밝게 섞은 색이고, 카운터 테두리와 패널은 원래 색이다.
10. **파일 구조.** 계획의 구조에 `ui/dom.ts`(DOM 도우미)가 더해졌고, `ui/`는 `game.ts`(게임 화면 조립), `join.ts`, `lobby.ts`, `topbar.ts`, `panel.ts`, `toast.ts`다.
11. **테스트용 핸들 `window.sandtable`.** 게임 화면 객체를 노출한다. Playwright가 카운터·프로빈스의 화면 좌표와 저장소 상태를 읽는 데 쓴다.
12. **개발 의존성 추가.** `@playwright/test`(종단 테스트), `@types/node`(설정 파일 타입 검사). 런타임 의존성은 계획대로 두 개다. 버전은 TypeScript 7, Vite 8, Vitest 5.
13. **테스트.**
    - `npm test`(Vitest): 저장소의 스냅샷/델타 적용(추가, 변경, `DESTROYED`, `OUT_OF_SIGHT`, 틱 건너뜀, 0값 필드의 레코드 교체), 재접속(2초 간격, 틱 건너뜀 시 즉시, 토큰 재사용, fatal 처리), Voronoi·카메라·진행도 계산.
    - `src/sync.integration.test.ts`: `SANDTABLE_WS`가 있을 때만 돈다. 실제 서버와 200틱 넘게 전투를 진행한 뒤, 델타로 만든 뷰가 새 스냅샷과 같은지 본다 (`e2e_test.go`와 같은 검사를 클라이언트 쪽에서).
    - `npm run e2e`(Playwright): 서버를 8091에 새 방으로 직접 띄운다 (`make build` 필요). 탭 두 개로 §1 완료 기준을 처음부터 끝까지 돌리고, M4 조작과 거부된 접속을 확인하며, 단계마다 `client/test-results/screens/`에 스크린샷을 남긴다.
14. **서버 쪽.** `match.Info()`를 추가하면서 `Snapshot()`과 같은 "방 고루틴에서 읽기" 코드를 `read()`로 묶었다. 정적 파일 디렉토리는 서버 시작 시점에 있어야 한다 (나중에 빌드하면 서버를 다시 띄운다). `/api/match`에 `id`가 없거나 없는 방이면 `404`.
15. **Vite 파일 감시는 항상 폴링**(`usePolling`, 300ms)이다. 이 레포가 Windows 드라이브에 있어 Windows 쪽 편집기의 변경을 inotify가 못 보기 때문이다. 폴링으로 CSS 수정이 약 0.2초 만에 반영되는 것은 확인했고, 폴링 없이 되는지는 확인하지 않았다.
