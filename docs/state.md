# 상태 모델

## 1. 세 층

| 층 | 내용 | 변경 | 해시 |
|---|---|---|---|
| 정적 데이터 `World` | 프로빈스 그래프, 지형, 유닛 타입, 규칙 상수, 시나리오 | 방 생성 후 불변 | 데이터 해시 |
| 동적 상태 `State` | 틱, 프로빈스 통제, 사단 | `Step`만 변경 | 상태 해시 |
| 뷰 `View` | 플레이어 한 명에게 보이는 `State`의 부분 | 매 틱 `State`에서 파생 | 없음 (저장 안 함) |

`Step(World, State, 명령) → State'`가 유일한 상태 전이다.

## 2. ID와 단위

| 대상 | 표현 |
|---|---|
| 프로빈스, 지형, 유닛 타입 | 데이터 파일에서는 문자열 키(`p03`, `hills`, `infantry`). 로드할 때 키 사전순으로 정렬해 0부터 정수 ID를 붙인다 |
| 진영 | 같은 방식으로 1부터. `0`은 "없음" |
| 사단 | 1부터 순차 발급 (시나리오에 적힌 순서). 재사용하지 않는다 |
| 시간 | 틱 (1틱 = 1시간) |
| 거리 / 속도 | km / km÷틱 (정수) |
| 비율 | 천분율 ‰ (1000 = 100%) |
| 병력, 조직력 | 정수 포인트 |

## 3. 정적 데이터 (`data/`)

```
data/
├── rules.yaml             # 전투·보급·시야 상수, 지형 타입
├── units.yaml             # 유닛 타입
├── maps/sample.yaml       # 프로빈스 + 간선
└── scenarios/sample.yaml  # 맵 참조, 진영, 초기 통제, 초기 사단
```

```yaml
# maps/sample.yaml
provinces:
  - {id: p01, name: Ashford, terrain: plains, pos: [120, 80], hub: true}
edges:
  - [p01, p02, 40]          # a, b, 거리(km). 양방향

# units.yaml
- id: infantry
  max_strength: 10000
  max_org: 1000
  attack: 60
  defense: 200              # 받는 피해 감소 (‰)
  speed: 4                  # km/틱
  org_recovery: 10          # 틱당, 보급 100% 기준
  width: 20                 # 전투 폭
  reinforce_chance: 20      # 예비대에서 전선으로 합류할 틱당 확률 (‰)

# scenarios/sample.yaml
map: sample
factions:
  - {id: azure, name: Azure League, provinces: [p01, p02, p03]}
divisions:
  - {faction: azure, type: infantry, name: 1st Infantry, at: p01}
```

- 인접은 `edges`에 한 번만 적는다. 프로빈스마다 인접 목록을 따로 쓰면 한쪽만 적는 비대칭 실수가 생긴다.
- 로더(`internal/gamedata`)가 검증한다: 중복 키, 없는 참조, 중복/자기 간선, 범위 밖 수치, 모르는 필드는 모두 오류.
- **데이터 해시** = 로드와 검증을 마친 `World`의 정규 인코딩에 대한 SHA-256. 파일 바이트가 아니라 내용 기준이라 주석이나 공백을 고쳐도 변하지 않는다. 로그와 스냅샷 헤더에 기록한다.

## 4. 동적 상태 (`State`)

| 필드 | 타입 | 설명 |
|---|---|---|
| `tick` | u64 | 진행된 틱 수. 시작은 0 |
| `seed` | u64 | 방의 시드 |
| `next_division_id` | u32 | 다음에 발급할 사단 ID |
| `provinces[]` | | 프로빈스 ID 순 |
| · `controller` | u8 | 통제 진영 (0 = 없음) |
| · `in_battle` | bool | 직전 전투 단계에서 공격받고 있었는가 |
| `divisions[]` | | 사단 ID 오름차순 |
| · `id` / `faction` / `type` | u32 / u8 / u16 | |
| · `name` | string | 표시용 |
| · `location` | u32 | 현재 프로빈스 |
| · `strength`, `org` | i32 | 병력, 조직력 |
| · `supply` | i32 | 마지막으로 계산한 보급 수준 (‰) |
| · `retreating` | bool | 후퇴 중 |
| · `attack_role`, `defense_role` | u8 | 공격하는 전투 / 자기 프로빈스 방어 전투에서의 위치. 0 = 참가 안 함, 1 = 예비대, 2 = 전선 |
| · `path[]` | u32[] | 남은 경유지. 맨 앞이 다음 프로빈스. 비어 있으면 정지 |
| · `progress` | i64 | 다음 프로빈스까지 누적한 진행도 |

저장하지 않는 파생 값: 프로빈스별 사단 목록, 보급 거리, 시야. 필요할 때 `State`에서 다시 계산한다 (순수 함수이므로 캐시해도 결과가 같다).

## 5. 정규 인코딩

`State`를 바이트열로 바꾸는 방법은 하나뿐이다.

- 정수는 고정 폭 little-endian, `bool`은 1바이트(0/1), 문자열과 배열은 `u32 길이 + 원소`.
- 맨 앞에 형식 버전(u32), 이어서 §4의 표 순서대로 쓴다.
- 같은 상태는 항상 같은 바이트가 된다.

이 바이트열을 세 곳에서 쓴다: **상태 해시의 입력**, **스냅샷 본문**, 그리고 명령 레코드도 같은 방식으로 인코딩한다. 인코더가 하나이므로 "스냅샷에 들어가는 것 = 해시가 덮는 것"이 보장된다.

## 6. 뷰 (플레이어에게 보이는 상태)

시야 규칙(전장의 안개)이 "무엇을 알 수 있는가"를 정하고([rules.md §7](rules.md)), 뷰 필터가 그 결과만 전송한다.

| 대상 | 누구에게 | 보이는 것 |
|---|---|---|
| 정적 데이터 (맵 전체) | 전원 | 전부 |
| 프로빈스 통제자 | 전원 | `controller` |
| 프로빈스의 전투 여부 | 시야 안 | `in_battle` |
| 자기 사단 | 본인 | 전체 필드 |
| 타 진영 사단 | 시야 안 | 위치, 타입, 이름, 병력, 조직력, 후퇴 여부. 경로·진행도·보급은 숨김 |

뷰 계산(`internal/view`)은 `State`를 읽기만 하고, 결과가 시뮬레이션으로 되돌아가지 않는다. 그래서 해시 대상이 아니다.
