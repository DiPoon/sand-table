# 틱 구조

## 1. 실행 모델

- **방(match) 하나 = 고루틴 하나.** 이 고루틴만 시뮬레이션 상태를 읽고 쓴다. 락이 없다.
- 접속(세션)마다 읽기·쓰기 고루틴이 있고, 방과는 채널(방의 inbox, 세션의 송신 큐)로만 통신한다.
- 시뮬레이션 코어(`server/internal/sim`)는 네트워크·시간·파일을 모른다. 진입점은 둘이다.
  - `Validate(world, state, cmd) → 거부 사유` : 상태를 바꾸지 않는 검증
  - `Step(world, state, cmds) → 결과` : 한 틱 진행
- 서버 프로세스는 방을 여러 개 담을 수 있는 구조지만, 1단계는 시작할 때 설정으로 방 1개를 만든다.

## 2. 한 틱

방 루프는 inbox(접속/이탈, 명령, 일시정지/배속)를 **틱 사이에만** 처리하고, 실행 중이면 틱 간격마다 아래를 수행한다. 현재 틱이 `T`일 때:

| # | 단계 | 내용 |
|---|---|---|
| 1 | 명령 확정 | 큐의 명령을 접수 순서대로 꺼내 틱 `T+1`의 입력으로 확정하고, 명령 로그에 **먼저** 기록한다 (write-ahead) |
| 2 | `Step` | 결정론 코어. 아래 2.1~2.6 |
| 2.1 | 틱 증가 | `tick = T+1` |
| 2.2 | 명령 적용 | 순서대로 재검증 후 적용. 실패는 거부 결과로 반환 |
| 2.3 | 이동과 점령 | 진행도 누적, 도착 처리. 다음 프로빈스에 적이 있으면 들어가지 않고 공격한다. 도착한 프로빈스의 통제자 변경 |
| 2.4 | 보급 | 진영별 보급 수준 계산 → 사단에 반영. 보급 0이면 병력 소모 |
| 2.5 | 전투 | 공격받는 프로빈스마다 한 라운드. 소멸, 후퇴, 공격 중단 처리 |
| 2.6 | 회복 | 전투에 참가하지 않은 사단의 조직력 회복 |
| 3 | 해시 | `tick % hash_interval == 0`이면 상태 해시를 로그에 기록 |
| 4 | 스냅샷 | `tick % snapshot_interval == 0`이면 스냅샷 저장 |
| 5 | 동기화 | 플레이어별로 시야 필터 → 직전에 보낸 뷰와 비교 → `Delta` 전송 |

각 단계 안에서 개체는 항상 ID 오름차순으로 처리한다. 규칙 세부는 [rules.md](rules.md), 3~4는 [persistence.md](persistence.md), 5는 [protocol.md §5](protocol.md).

## 3. 시간, 배속, 일시정지

- **1틱 = 게임 시간 1시간.** 틱은 게임 시간의 고정 단위다. 배속은 "실시간 1초에 틱을 몇 번 돌리는가"만 바꾸므로 시뮬레이션 결과에 영향이 없고, 명령 로그에도 기록하지 않는다.
- 배속 5단계 (서버 설정, 아래는 기본값):

  | 배속 | 1 | 2 | 3 | 4 | 5 |
  |---|---|---|---|---|---|
  | 틱 간격 | 1000ms | 500ms | 250ms | 100ms | 50ms |

- 틱 처리가 간격보다 오래 걸려도 밀린 틱을 몰아서 따라잡지 않는다. 다음 틱을 곧바로 시작할 뿐이다 (게임이 느려질 뿐 결과는 같다).
- **방의 단계**: `LOBBY`(진영 선택, 틱 정지) → 호스트가 시작 → `RUNNING`. 시작한 뒤에도 비어 있는 진영으로 언제든 참여할 수 있다.
- **호스트**는 접속해 있는 참가자 중 가장 먼저 들어온 사람이다. 호스트가 나가면 그다음 사람이 호스트가 된다.
- 배속 변경과 시작은 호스트만, 일시정지와 재개는 참가자 누구나 할 수 있다. 바뀌면 방 전체에 `MatchStatus`를 보낸다.
- 복구한 방은 `RUNNING` 단계의 일시정지 상태로 시작한다. 접속자가 0명이 되면 자동으로 일시정지한다.

## 4. 명령 큐

```
Command ─▶ 세션(디코드) ─▶ 방 inbox ─▶ Validate(현재 상태)
                                        ├─ 실패: CommandResult{REJECTED, reason} 즉시 회신
                                        └─ 통과: 큐에 추가, CommandResult{ACCEPTED, apply_tick = T+1}

다음 틱:  큐 ─▶ 명령 로그 ─▶ Step 안에서 재검증 후 적용
                              └─ 이때 실패하면 그 틱에 CommandResult{REJECTED, reason}
```

- 일시정지 중에도 명령을 접수한다. 재개 후 첫 틱에 적용된다.
- 적용 순서는 방 고루틴이 접수한 순서다. 이 순서가 로그에 그대로 남으므로 리플레이에서도 같다.
- 검증을 두 번 하는 이유: 접수 시 검증은 빠른 피드백용이고, **적용 시 검증이 권위**다. 리플레이는 적용 시 검증만 다시 수행하므로 라이브와 같은 결과가 나온다.
- 진영당 대기 명령은 256개까지. 넘으면 `QUEUE_FULL`로 거부한다.

## 5. 결정론 규칙 (`sim` 패키지)

1. **정수만.** 게임 수치는 고정 폭 정수(`int32`, `int64` 등)다. `float`는 금지. `int`는 플랫폼마다 폭이 다르므로 슬라이스 인덱스와 길이에만 쓴다. 비율은 천분율(‰) 정수.
2. **계산 순서 고정.** 곱한 뒤 나눈다. 나눗셈은 0 방향 버림. 중간값은 `int64`. 공식의 연산 순서도 규칙의 일부다.
3. **난수는 키 기반 PRNG만** 쓴다 (§6).
4. **`map` 금지.** 순회 순서 문제를 원천 차단한다. ID로 인덱싱하는 슬라이스를 쓰고, 순회는 항상 ID 오름차순이다.
5. **시간·동시성·I/O 금지.** `time`, 고루틴, 채널, 전역 가변 상태, 파일, 네트워크를 쓰지 않는다. import는 허용 목록(`errors`, `fmt`, `slices`, `math/bits`, `encoding/binary`, `crypto/sha256` 등)만 가능하다.
6. **강제.** 테스트가 `sim` 패키지 소스를 AST로 검사해 `float`, `map`, `go` 문, 허용 목록 밖 import를 잡는다.

## 6. 난수

난수는 저장된 PRNG 상태에서 뽑지 않고 키에서 파생한다: `PRNG(seed, tick, 용도, 개체 ID)` (SplitMix64 기반).
예를 들어 전투에서 사단 17이 이번 틱에 쓰는 난수열은 `PRNG(seed, tick, COMBAT, 17)`이다.

- 개체 처리 순서나 다른 시스템의 난수 사용량이 바뀌어도 값이 흔들리지 않는다.
- PRNG 상태를 스냅샷에 넣을 필요가 없다. 시드만 있으면 된다.

## 7. 상태 해시

`상태 해시 = SHA-256(State의 정규 인코딩)`. 정규 인코딩은 [state.md §5](state.md)에 있다.
`hash_interval`(기본 24)틱마다 로그에 기록하고, 복구와 리플레이 때 대조한다.

## 8. 테스트와 측정

결정론 테스트 (`sim` 패키지, 네트워크 없이):

- 같은 시드 + 같은 명령 스크립트로 두 번 실행하면 매 틱 해시가 같다
- 스냅샷 저장 → 복원 → 이어서 실행한 결과가 중단 없이 실행한 결과와 같다
- 명령 로그 리플레이 결과가 라이브 실행과 같다
- 골든 해시: 고정된 시나리오·시드·스크립트의 최종 해시를 상수로 박아 둔다 (다른 아키텍처에서도 같아야 한다)
- 시드가 다르면 해시가 달라진다 (난수가 실제로 쓰이는지 확인)

측정:

- `BenchmarkStep` : 틱 1회 소요 시간. 샘플 맵, 그리고 코드로 생성한 큰 맵(프로빈스 1천 / 1만)에서 각각
- `BenchmarkHash`, `BenchmarkSnapshot`, `BenchmarkDelta` : 틱 밖에서 드는 비용
- 실행: `make bench`
- 런타임: 방 루프가 틱마다 `Step` / 동기화 / 전체 소요 시간을 재서 주기적으로 요약 로그를 남긴다 (시간 측정은 코어 밖에서만 한다)
